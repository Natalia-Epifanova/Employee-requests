# Employee Requests

Django-приложение для учета заявок сотрудников.

## Стек

- Python 3.11+
- Django 5.2
- PostgreSQL
- Django templates

## Что реализовано

- Справочники подразделений, должностей и сотрудников.
- Создание заявок с номером, датой создания, автором, исполнителем, описанием, сроком выполнения и статусом.
- Изменение статуса заявки с проверкой допустимых переходов.
- Изменение исполнителя заявки.
- Список заявок с фильтрами по статусу, исполнителю, подразделению и просроченности.
- Отчеты по статусам, просроченным заявкам и выполненным заявкам по исполнителям.
- Генерация тестовых данных: минимум 1000 сотрудников и 1 000 000 заявок.
- Замер производительности целевого запроса до и после оптимизации.

## Запуск проекта

1. Создать и активировать виртуальное окружение:

```powershell
python -m venv venv
.\venv\Scripts\activate
```

2. Установить зависимости:

```powershell
pip install -r requirements.txt
```

3. Создать PostgreSQL-базу данных, например `requests`.

4. Создать файл `.env` по примеру `.env.example`:

```env
SECRET_KEY=your-secret-key
DEBUG=True
DATABASE_NAME=requests
DATABASE_USER=postgres
DATABASE_PASSWORD=your-password
DATABASE_HOST=localhost
DATABASE_PORT=5432
```

5. Применить миграции:

```powershell
python manage.py migrate
```

6. Создать суперпользователя:

```powershell
python manage.py createsuperuser
```

В текущей тестовой базе был создан пользователь:

```text
login: admin
password: admin_password
```

7. Запустить сервер:

```powershell
python manage.py runserver
```

## Бизнес-процесс

Заявка проходит три статуса:

```text
Новая -> В работе -> Выполнена
```

При создании заявка получает статус `Новая`. Далее ее можно перевести только в следующий разрешенный статус. Прямой переход из `Новая` в `Выполнена` запрещен.

## Бизнес-правила

- Заявку из статуса `Новая` можно перевести только в `В работе`.
- Заявку из статуса `В работе` можно перевести только в `Выполнена`.
- Заявка в статусе `Выполнена` больше не меняет статус.
- Если выбран тот же статус, форма не считает это ошибкой.
- Просроченной считается заявка, у которой срок выполнения меньше текущей даты и статус не равен `Выполнена`.
- Исполнителя заявки можно изменить отдельно от статуса.

## Структура базы данных

Используются основные сущности:

- `Department` - подразделение.
- `Position` - должность.
- `Employee` - сотрудник.
- `Request` - заявка.

Связи между сущностями:

- `Employee.department` связан с `Department` через внешний ключ.
- `Employee.position` связан с `Position` через внешний ключ.
- `Request.author` связан с `Employee` через внешний ключ.
- `Request.assignee` связан с `Employee` через внешний ключ.

Такое разделение уменьшает дублирование данных. Например, название подразделения хранится один раз в таблице подразделений, а сотрудники только ссылаются на него. То же самое сделано для должностей. В заявке не дублируются ФИО автора и исполнителя, а хранятся ссылки на сотрудников.

## Генерация тестовых данных

Команда для заполнения базы:

```powershell
python manage.py seed_test_data
```

По умолчанию команда создает:

- 10 подразделений.
- 20 должностей.
- не менее 1000 сотрудников.
- не менее 1 000 000 заявок.

Для быстрой проверки можно передать меньшие значения:

```powershell
python manage.py seed_test_data --employees 10 --requests 100 --batch-size 20
```

## Замер производительности

Целевой запрос из задания:

```text
вывести все просроченные заявки конкретного исполнителя,
находящиеся в статусе "В работе",
отсортированные по сроку выполнения
```

Команда замера:

```powershell
python manage.py measure_overdue_requests --assignee-id 1 --explain
```

Запрос фильтрует заявки по исполнителю, статусу и сроку выполнения, а затем сортирует по сроку:

```python
Request.objects.filter(
    assignee_id=assignee_id,
    status=Request.Status.IN_PROGRESS,
    due_date__lt=timezone.localdate(),
).order_by("due_date")
```

## Оптимизация базы данных

Сначала явные индексы в модели не использовались, чтобы можно было показать разницу до и после оптимизации.

После первичного замера была добавлена отдельная миграция `0002_request_request_status_idx_and_more.py` с индексами:

- индекс по `status`;
- индекс по `due_date`;
- составной индекс по `assignee`, `status`, `due_date`.

Отдельный индекс по `assignee` не добавлялся вручную, потому что Django автоматически создает индекс для внешнего ключа `ForeignKey` на исполнителя. Повторный ручной индекс дублировал бы уже существующий индекс.

Дополнительно в списках заявок и сотрудников возвращен `select_related`. Это ORM-оптимизация: связанные объекты подтягиваются одним SQL-запросом через `JOIN`, а не отдельными запросами при обращении к каждому объекту.

Результаты замера на тестовой базе с 1 000 000 заявок:

| Этап | Rows found | Python elapsed | PostgreSQL Execution Time |
| --- | ---: | ---: | ---: |
| До оптимизации | 167 | 0.015371 s | 2.510 ms |
| После оптимизации | 167 | 0.007879 s | 0.276 ms |

Почему стало быстрее:

- составной индекс `assignee, status, due_date` соответствует условиям фильтрации и сортировке целевого запроса;
- PostgreSQL может быстрее найти нужные строки по исполнителю и статусу;
- поле `due_date` в конце индекса помогает выбрать только просроченные заявки и отдать их в нужном порядке;
- `select_related` уменьшает количество SQL-запросов при отображении списков.

## Дополнительное задание

Если заявка должна проходить согласование руководителем, можно добавить отдельный статус, например `На согласовании`, и связь с руководителем. Бизнес-процесс станет длиннее: `Новая -> На согласовании -> В работе -> Выполнена`. Также потребуется правило, что согласовать заявку может только руководитель.

Если у заявки может быть несколько исполнителей, поле `assignee` нужно заменить на связь many-to-many между заявками и сотрудниками. При необходимости можно создать промежуточную модель, где будут храниться роль исполнителя, дата назначения и активность назначения.

Если нужно хранить историю изменения статусов, стоит добавить модель `RequestStatusHistory` с заявкой, старым статусом, новым статусом, датой изменения и пользователем, который выполнил изменение. Тогда текущий статус останется в заявке для быстрого доступа, а история будет хранить аудит изменений.

Если сроки выполнения зависят от типа заявки, нужно добавить модель `RequestType` с нормативным сроком выполнения. При создании заявки срок можно рассчитывать автоматически на основе выбранного типа.

Если требуется разграничение прав доступа, можно использовать стандартную систему пользователей, групп и разрешений Django. Например: сотрудник создает и просматривает свои заявки, руководитель согласовывает заявки своего подразделения, администратор управляет справочниками и всеми заявками.
